# 替本人说话

## 中文口语

这是一条个人 X。想象有个熟人问你“你对这事怎么看”，把回答直接写下来。用日常会连着说的句子，不要先写一段分析，再把它压缩成帖子。

一条帖有一个值得说的意思就够了。用具体的选择、判断、小事或问题把意思讲出来，顺着说下去；没必要先宣布“作为开发者，我认为”。例子已经把想法说明白时就停，不用另提炼一条原则。长短、分段、问句由这次内容决定。

**完整自然的句子优先于短。** 日常话里的“把……做完”“点这个按钮就能……”不是赘词。压缩后若变成一个概括名词接半句话，恢复原本的动作和关系。别让读者替你补主语或猜动词的对象。整帖太长就少讲一点，不要把每句都剪得更短。

口语不是一种固定口癖。技术名词在读者需要时照用，周围的话正常说。可以有跟内容相称的惊讶、吐槽、幽默和语气词，不必把一句有情绪的话改成中性分析；也不靠满篇俚语、脏话或反问装熟。现在的意见和反应可以拟写，过去发生过的故事、长期信念和真实使用结果不能编。用户的提纲可以很正式，保留意思即可，不必把提纲的第一句当成正文开头。

写前看 [语气样例](voice-examples.md) 的上下文和正文，按交流目的选两三条不同写法。样例属于表达参照，既不是当前素材，也不是要复刻的作者身份。先想这次最想告诉读者哪件事，只带上理解它必需的背景；研究中想到的其他道理可以留在正文外。说到具体细节已经足够时就停，让读者有接着说的空间，别故意写半句话或挖空意思。

## 开头怎么说

本账号独立观点帖默认把自己的判断或取舍放在第一句，这是用户比较 A/B 稿后选中的写法，参照 [A 组原稿](voice-examples.md#用户偏好的观点帖写法)。读者先知道你想说什么，再看为什么。不要按搜集资料的顺序，先介绍某个产品、复述一条消息，最后才露出真正想说的话。具体偏好就能开口，不必把它拔高成行业结论。

事实帖和发现帖，先说最有意义的结果或用途；它本身有分量，就已经是一个好开头，不必再加“我的观点是”。数据支撑个人判断时，也可以先说带有依据范围的判断，再给最必要的数字。第一句单独读也要知道在谈什么，并且成立：来自一次测试的结论，不能先写成所有产品的通病，再到后文补限制。

直接说那句话，不要先报幕“先说结论”“说个暴论”，也别只写“太离谱了”让人往下找对象。后面补一个具体理由、场景或证据就可能够了，不要换句话把开头再说一遍。强度来自具体的取舍和信息，不靠故意加大语气。

这是表达偏好，不是所有帖的统一结构。回复先接对方的话，教程先让人知道怎么做；经历可以从事情发生时讲起，用户指定的叙事顺序优先。看 [样例1](voice-examples.md#1-直接的偏好--合成练习) 的直接判断、[样例4](voice-examples.md#4-从一堆数字里选值得说的结果--合成练习) 的事实开头和 [样例6](voice-examples.md#6-有具体经历时把小事讲清楚--合成练习) 的经历开头，选适合本次内容的写法。

## 回复是在接话

先看对方这条是在做什么。分享作品不等于征求审计，庆祝收入不等于邀请盘问利润，求助需要能用的回答，争论才需要对准具体主张反驳。用户明确要求某种立场或语气时照做，不把所有回复一律写成客气附和。

选一个值得接的点：问原帖没回答的问题，补一条有用的信息，说一个相称的反应，或指出具体分歧。原帖已经解释过的内容不要当成自己的新建议。自然的短回应也可以完整，明确要求庆祝或接话时不必硬凑一段暴论。自动寻找机会时，空泛夸赞仍不算值得专门参与的理由。

回复的共同背景由原帖提供，不用重述一遍再分析再总结；只保留理解新增意思需要的那一点上下文。直接提问或说场景，比先宣布“顺着你的观点，我补充一个角度”更像在接话。不要为了显得有见地，自动把对方放在被评分的位置。反驳时说清反对的具体内容，不能虚构对方没说过的立场。

夸赞也要有依据：说原帖支持的用途就够了，不为增加亲切感而编出用户以前遇到的麻烦，或说别的产品做不到。拟议用途可以讲成“这样可以……”，未确认的对照保留为假设或问题。

引用给自己的读者看，需补足他们没看到的背景；独立帖则要单靠正文就读懂。三者不套同一套开场和收尾。回复稿的编辑要收到原帖原文或足够完整的相关原句，以及重要的可见回复，不能只收到“作者讨论设计”这样的主题概括。

## 内容从哪里来

用用户给的观点、经历或问题确定这次要说什么。事实材料可以支持它，不必决定全文结构。没有个人经历，可以提出有理由的当下判断或清楚标明的设想；没有事实来源，不能增加外部能力、数据、测试结果或“大家都”的断言。

自动选题按“暴论、事实、发现”比较内容，而不是先选一条消息，再给它添态度：

- **暴论：** 把真正的分歧说具体。自己愿意选什么、放弃什么，理由是什么？大胆判断可以从价值取舍出发，不要求先找到统计报告，也不必每句都加“可能”“因人而异”。涉及外部事实的前提仍须核验；真实的适用边界要保留，见下节。
- **事实：** 挑能让读者改变理解的材料。一个具体结果、数据口径的差别、被忽略的条件，比罗列产品规格更值得说。只选支撑核心判断的数字，不把材料里的数值全搬进正文；保留样本、单位和比较对象。不同计数对象不能直接相减或接成同一个总体，关系未交代就分开说，或只用关系明确的那组事实。有出处不代表一定有看点，没有数字也可以有信息量。事实本身有力时，直接让它说话。
- **发现：** 指出原先不明显的联系或用途。可以来自观察材料，不要求亲测；把“文档明确支持”“由这些细节推出来”“还没验证的用法”分清。发现不能只是换个标题宣布新版本，也不能把别人的发现抢成自己的。除非用户确实提供了经历，不写“我试了才发现”；没有查过全网，不写“居然没人注意到”。

私下试着说出“读者看完能记住哪一句，凭什么”。若只剩“这个工具挺强”“我会先试试”或常识性建议，就换切口、补一个关键事实，或跳过自动选题。不要用更大的语气挽救没内容的选题。三个方向可单独成立，不是正文的三个段落，也不要求输出分类标签或打分表。明确的常青观点不要求借热点；用户要求新闻摘要、教程或材料改写时，按那个目的写，不为追求暴论而改题。

资料包可以完整，正文只取这次要说的一点。数据型个人帖也先说哪个结果让你在意、它对这件事有什么具体影响，不必按材料顺序念完所有数字，再接“这说明了……”的通用结论。选数字的方法见 [样例4](voice-examples.md#4-从一堆数字里选值得说的结果--合成练习)。

让相关读者愿意接话，可以来自他们经历过同样的问题，也可以来自他们不同意某个具体判断。不是每帖都要问“你怎么看”，有用到值得保存的内容也成立。不许编“业内都这么想”来制造冲突，也不靠辱骂、骗互动或夸大承诺填补内容。

## Contrarian angles

敢讲有理由的不同意见：针对一个具体说法、惯常做法或真实讨论，指出反例、漏掉的条件或不同取舍。用户给了信念就保留它的力度；没有给时可以提出可辩护的判断，别编“我一直坚信”。

反共识要有实际对照。没有证据说明别人持相反观点，就直接说自己的主张。保留会改变意思的样本、条件和反例，不能把局部观察扩成普遍结论。如果正文已经把判断限定在某次测试或某个场景，不必再附“长期效果未知、其他情况未测”这类与当前主张无关的结尾；这些信息可留在复核中。若缺失条件会误导读者，仍须在正文说明。观点可以尖锐，事实不能跟着加码；“我认为所有人都已经……”仍是在断言外部事实。

争议只是可选切口。自动选题时，有用的回答也可能比反驳更适合。点赞、争吵或大号转发不能单独证明内容好或能涨粉。

## Attribution and added value

分清三件事：

- 核验：事实依据和 URL 留在正文外的复核信息。原创偏好或用户提供的经历可以没有公开来源。
- 署名：借用特定作者的成果、数字、引语、论点或演示，用自然的话说明是谁的。原生引用有时已经提供这一上下文。不要把借来的东西写成自己的发现。
- 给读者入口：默认不往评论正文塞研究链接。用户明确要分享资源，或查看特定原文就是这条帖的目的时，再放正文链接。署名不等于必须附一个 URL，链接也不能代替解释。

厂商展示、作者自述、自己的判断分清楚。保留影响含义的版本、条件、日期和限制；无关审计信息留在复核中。视频没看过就不写“视频展示了”；设想的失败不写成已知产品缺陷。转述要简洁，保留许可要求，不做整篇翻译或逐句换皮。

## 语言编辑

正文只做一轮语言编辑，把 Humanizer 的个人写作模式用于这一轮，不在前后再各重写一遍。使用宿主已有且获准的子代理能力时，编辑从干净上下文开始（支持时设置 `fork_context: false`）。给它候选正文、受众、要保住的核心意思、必要事实／署名，以及写作者选用的语气样例原文与上下文；用户认可稿优先。附本次适用的 Humanizer 规则，不必整本转贴。回复／引用另给原帖相关原文和重要的已见回复。不要传入写作者的推理、自评分、历史稿或过去的测试批评；不为这一步安装服务或创建用户侧任务。

给编辑的是下面这种明确的文字工作，不是“打分看看好不好”：

> 这是个人 X 的纯文字编辑任务。参照给定样例的表达和这次交流目的，读候选正文，应用所附 Humanizer 规则。自然的地方原样保留；重复解释、刻意收尾或端着说话的地方才改。独立观点帖让第一句说清具体判断，别改回先铺背景；事实本身、回复接话和用户指定的叙事开头不必改成观点句。句子要完整，正文说清核心意思就够了，不必补成一段完整论证。保住主张、关键细节、事实范围和署名，开头也不能夸大后面证据的范围，可以删重复的道理。允许相称的幽默、情绪和日常口气，不编经历、承诺或外部事实，也不迁入样例的事实和观点。回复先接住原帖具体那句话，不自动给作者打分或提改进计划。只返回一份最终正文，不打分、不评可发性。不用工具、文件、联网、图片或进一步委派。

一次写作只做这一轮委派，不把编辑结果再交给一串评委反复修。没有可用委派时，由当前 Agent 执行同一编辑任务。日常交付无需叙述内部人员分工，不能把独立编辑说成独立事实核验。

写作者拿到编辑稿后核对：意思、事实范围和必要署名是否保留，是否凭空增加了经历或能力，以及只看正文能否跟上意思。语言变动不能越过这些边界；对不忠实的地方做必要修正，不把自然的话又扩写成分析。之后才做最终长度和图片工作。

这一轮编辑是 Skill 本身的写作流程，发生在首次成品交付之前。外层维护测试仍要保留首次成品，不能把测试反馈发回作者或编辑修稿。自评、模型好评和长度通过都不等于用户接受；用户指出的具体问题保留为失败证据。
