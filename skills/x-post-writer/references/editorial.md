# 替本人说话

## 中文口语

这是一条个人 X。先看眼前是什么事、你准备对谁说哪句话。默认是参与者在说话，不是采访者、顾问或资料讲解员。分享一个好玩的东西、接住一句话、讲出不满、认真提问，都可以成立。用日常会连着说的句子，别先写一段议论，再把它压缩成帖子。

一条帖有一个值得说的意思就够了。先用平常聊天的方式直接说出那个意思，再补缺了会让人误解的背景。不要先铺“这个例子很有意思”，也不必把已经明显的反差拆成几步给读者讲明白。对材料有反应就直接说：赞同、怀疑、觉得好笑、看不惯，都可以。观点不用每次缓和成“我更想看／要是能讲讲就好了”。用具体的选择、判断、小事或问题把意思讲出来，顺着说下去；没必要先宣布“作为开发者，我认为”。例子已经把想法说明白时就停，不用另提炼一条原则。长短、分段、问句由这次内容决定。

**完整自然的句子优先于短。** 日常话里的“把……做完”“点这个按钮就能……”不是赘词。压缩后若变成一个概括名词接半句话，恢复原本的动作和关系。别让读者替你补主语或猜动词的对象。整帖太长就少讲一点，不要把每句都剪得更短。

口语不是一种固定口癖。技术名词在读者需要时照用，周围的话正常说。可以有跟内容相称的惊讶、吐槽、幽默和语气词，不必把一句有情绪的话改成中性分析；也不靠满篇俚语、脏话或反问装熟。可以根据账号方向自主构思当下判断、偏好或吐槽，不必证明用户以前就这样想。第一人称故事可按下文的创作授权写；事实型任务仍保留给定材料的范围。用户的提纲可以很正式，保留意思即可，不必照抄提纲开头。

需要样例时，按交流目的选 [语气样例](voice-examples.md)，不为每条固定加载同一组偏好句。样例不是当前素材或要复刻的身份。只带上理解本次表达必需的背景；一条帖可以只分享一个发现、一处不满或半段仍值得聊的想法，不用替读者把所有后续问题都答完，但当前这句话仍须完整可懂。细节要承担作用：说明为什么在意、让人理解取舍、改变故事的局面；技术名词和数字不因显得正式而自动删。批量稿如果都在“亮态度—说明理由—漂亮收口”，要看最后一句是否真的有事可说，而不是为了每条长短不同硬添或删字。不要固定站在比原帖更清醒的位置。

## 开头怎么说

用户喜欢有观点时尽早亮出来，参照 [A 组原稿](voice-examples.md#用户偏好的观点帖写法)。把自己根据材料形成的判断放前面，不按资料搜集顺序绕一遍。没有用户预先给的立场也能提出主张，不必专门编一段经历来替主张作证。眼前的事、反应和问题也能直接开口，立场可以从说了什么、怎么接话里显出来。

事实帖和发现帖，先说最有意义的结果或用途；它本身有分量，就已经是一个好开头，不必再加“我的观点是”。数据支撑个人判断时，也可以先说带有依据范围的判断，再给最必要的数字。第一句单独读也要知道在谈什么，并且成立：来自一次测试的结论，不能先写成所有产品的通病，再到后文补限制。

直接说那句话，不要先报幕“先说结论”“说个暴论”，也别只写“太离谱了”让人往下找对象。后面补一个具体理由、场景或证据就可能够了。读最后一句时，判断它是否增加条件、推进动作或改变前文的意思：这些作用值得留；只是把同一个用途、好处或态度再说一遍，就删掉重复部分。反转不是通用总结，事实的限制也不是赘词。参照 [结尾的作用](voice-examples.md#结尾的作用--合成对照)，不机械禁止总结或强制造一个笑点。强度来自具体的取舍和信息，不靠故意加大语气。

这是表达偏好，不是所有帖的统一结构。回复先接对方的话，教程先让人知道怎么做；经历可以从事情发生时讲起，用户指定的叙事顺序优先。参照 [语气样例](voice-examples.md) 中实际相近的交流目的，不必固定一种开头。

## 回复是在接话

先看对方这条是在做什么。分享作品不等于征求审计，庆祝收入不等于邀请盘问利润，求助需要能用的回答，争论才需要对准具体主张反驳。用户明确要求某种立场或语气时照做，不把所有回复一律写成客气附和。

选一个值得接的点：说一个相称的反应，补信息或不同看法，或者问一个真想知道的具体问题。不要默认以“能不能再讲讲”“我更想看”向作者索取下一篇内容；想看更多不是自动成立的新观点。原帖已经解释过的内容不要当成自己的新建议。自然的短回应也可以完整，明确要求庆祝或接话时不必硬凑一段暴论。自动寻找机会时，空泛夸赞仍不算值得专门参与的理由。

回复的共同背景由原帖提供，不用重述一遍再分析再总结；只保留理解新增意思需要的那一点上下文。直接提问或说场景，比先宣布“顺着你的观点，我补充一个角度”更像在接话。不要为了显得有见地，自动把对方放在被评分的位置。写“得……”“应该……”前，确认对方真在问怎么办，或当前主张确实需要反驳；自己的反应不必写成对别人的建议。已经用一个细节把意思讲出来，就别接着解释这个细节证明了什么。反驳时说清反对的具体内容，不能虚构对方没说过的立场。

夸赞也要有依据：说原帖支持的用途就够了，不自动加一段自己的遭遇，或说别的产品做不到。拟议用途可以讲成“这样可以……”，未确认的对照保留为假设或问题。

引用给自己的读者看，需补足他们没看到的背景；独立帖则要单靠正文就读懂。三者不套同一套开场和收尾。回复稿的编辑要收到原帖原文或足够完整的相关原句，以及重要的可见回复，不能只收到“作者讨论设计”这样的主题概括。

## 内容从哪里来

用户给了观点、经历或问题就使用；没给也能从账号方向自主选题、提出判断。可以纯观点、反例、吐槽或假设，不需要先补一段亲身经历。事实材料支持相应事实，不决定全文结构；没有来源就不增加具体外部能力、数据、测试结果或“大家都”的断言。

开放选题按 [angles.md](angles.md) 比较不同主张，先选出值得说的内容，再参考语气样例写正文。“自然、通顺”和“有信息、有判断”分开检查：一条完全正确的常识，也可能没有自动推荐给读者的理由。观点在第一句只改变顺序，不会自动增加内容的分量。

明确的常青观点不要求借热点；用户指定新闻摘要、教程、庆祝或材料改写时，按那个目的写。很小的偏好也可以按要求表达，不把开放选题的筛选门槛变成拒绝用户明确任务的理由。

数字只取支撑核心意思的部分，保留样本、单位和比较对象。不同计数对象不能直接相减或接成同一个总体，关系未交代就分开说，或只用关系明确的那组事实。发现可来自观察材料，不要求亲测；分清文档支持的能力、推出来的用途和已验证的结果。转述事实材料时，不把别人的测试改成“我试了才发现”，也不凭空加“居然没人注意到”。

资料包可以完整，正文只取这次要说的一点。数据型个人帖也先说哪个结果让你在意、它对这件事有什么具体影响，不必按材料顺序念完所有数字，再接“这说明了……”的通用结论。选数字的方法见 [数字样例](voice-examples.md#从数字里挑出真正有用的结果)。

让相关读者愿意接话，可以来自他们经历过同样的问题，也可以来自他们不同意某个具体判断。不是每帖都要问“你怎么看”，有用到值得保存的内容也成立。不许编“业内都这么想”来制造冲突，也不靠辱骂、骗互动或夸大承诺填补内容。

## 创作与事实任务

本账号允许创作性代写：日常小事、第一人称经历和人物对话可以编，正文可以直接说“我昨天……”，不必用“假如／想象一下”开场或加虚构声明。是否写故事取决于内容；不要为了利用这项授权，把每个观点改成亲历、把每条都写成段子。情节服务于想说的话，少塞无关细节，不在故事后补一段人生道理。

这项授权随本账号的普通创作调用沿用；其他账号按各自要求。用户指定真实、实测、仅按材料改写，或当前任务是在转述某份事实来源时，按事实写作，不借创作授权改动数据、归属和条件。真实产品能力、外部新闻、来源链接与执行结果仍须有相应依据。

把创作范围一起传给语言编辑：哪些情节可编，哪些事实要保留。编辑不能把已授权的第一人称故事一律改回假设场景。复核与历史记录中，创作情节不算真实用户经历、测试证据或实际工具操作；无需把内部分类塞进正文，也不把创作情节存成用户履历。

## Contrarian angles

敢讲有理由的不同意见：针对一个具体说法、惯常做法或真实讨论，指出反例、漏掉的条件或不同取舍。用户给了信念就保留它的力度；没有给时可以提出可辩护的判断，别编“我一直坚信”。

反共识要有实际对照。没有证据说明别人持相反观点，就直接说自己的主张。保留会改变意思的样本、条件和反例，不能把局部观察扩成普遍结论。如果正文已经把判断限定在某次测试或某个场景，不必再附“长期效果未知、其他情况未测”这类与当前主张无关的结尾；这些信息可留在复核中。若缺失条件会误导读者，仍须在正文说明。观点可以尖锐，事实不能跟着加码；“我认为所有人都已经……”仍是在断言外部事实。

争议只是可选切口。自动选题时，有用的回答也可能比反驳更适合。点赞、争吵或大号转发不能单独证明内容好或能涨粉。

## Attribution and added value

分清三件事：

- 核验：事实依据和 URL 留在正文外的复核信息。原创观点、用户提供的经历或授权创作可以没有公开来源，创作不充当核验依据。
- 署名：借用特定作者的成果、数字、引语、论点或演示，用自然的话说明是谁的。原生引用有时已经提供这一上下文。不要把借来的东西写成自己的发现。
- 给读者入口：默认不往评论正文塞研究链接。用户明确要分享资源，或查看特定原文就是这条帖的目的时，再放正文链接。署名不等于必须附一个 URL，链接也不能代替解释。

厂商展示、作者自述、自己的判断分清楚。保留影响含义的版本、条件、日期和限制；无关审计信息留在复核中。视频没看过就不写“视频展示了”；设想的失败不写成已知产品缺陷。转述要简洁，保留许可要求，不做整篇翻译或逐句换皮。

## 语言编辑

正文只做一轮语言编辑，把 Humanizer 的个人写作模式用于这一轮，不在前后再各重写一遍。使用宿主已有且获准的子代理能力时，编辑从干净上下文开始（支持时设置 `fork_context: false`）。给它用户的具体写作要求、是否属于开放选题、创作授权或事实限定、候选正文、受众、要保住的核心意思、必要事实／署名，以及实际选用的语气样例原文与上下文；只在交流目的相近时参考历史认可稿。附本次适用的 Humanizer 规则，不必整本转贴。回复／引用另给原帖相关原文和重要的已见回复。不要传入写作者的推理、自评分、历史稿或过去的测试批评；不为这一步安装服务或创建用户侧任务。

给编辑的是下面这种明确的文字工作，不是“打分看看好不好”：

> 这是个人 X 的纯文字编辑任务。按实际交流目的和所附 Humanizer 规则编辑，不强行套样例。自然的地方原样保留；改词义不顺、前后偷换对象、重复解释、端着说话或刻意收尾的地方。已有判断不必加长背景；分享、反应、提问和回复不用先改成一个取舍。保住意思、必要细节、事实范围和署名；不加一段道理，不添没有上下文的笑点来制造人味。保留具体反应的直接劲儿，不把它缓和成长段愿望或建议；意思已经说到时可以停，不必讲清所有理由。检查末句是否有新条件、新动作或反转；若只重复前面的用途或好处，删掉重复，不补一个更漂亮的总结。保留改变判断的限制和推动笑点的末句，不机械截短。允许相称的情绪；已授权的创作情节可以保留第一人称，不强加假设开头或虚构标签；事实型任务不添经历、关系或外部事实。回复接住原话，不自动给人打分或安排改进。只在开放选题时，若整条只有没有取舍的常识，或者只是复述原帖再补“实用／合理”而没有自己的意思，直说“退回选题：”并点明缺什么，不用润色掩盖；独立观点与授权故事都可以成立，不能因为没有用户亲身经历、原始立场或新闻来源就退回；用户明确给定的小立场、假设、教程或庆祝不因这条标准退回。否则只返回一份最终正文。不打分，不宣称可发，不用工具、文件、联网或进一步委派。

一次写作只做这一轮委派，不把编辑结果再交给一串评委反复修。被退回的候选不当成成品；若还有已找到的有效素材，可以回到选题另写一条。没有则按实际情况 skip 或 blocked，不拿另一个常识凑数，也不让同一编辑根据评分连续改稿。明确给定的教程、庆祝、立场不适用开放选题的退回标准。没有可用委派时，由当前 Agent 执行同一编辑任务。日常交付无需叙述内部人员分工，不能把独立编辑说成独立事实核验。

写作者拿到编辑稿后核对：意思、事实范围和必要署名是否保留，是否超出本次创作范围或增加了没有依据的产品能力，以及只看正文能否跟上意思。选中时有分量的那项取舍、反例或发现，也应仍在正文里；不能被润色成“各有优劣”“值得关注”或泛泛的使用建议。语言变动不能越过这些边界；对不忠实的地方做必要修正，不把自然的话又扩写成分析。之后才做最终长度和图片工作。

这一轮编辑是 Skill 本身的写作流程，发生在首次成品交付之前。外层维护测试仍要保留首次成品，不能把测试反馈发回作者或编辑修稿。自评、模型好评和长度通过都不等于用户接受；用户指出的具体问题保留为失败证据。
