# 替本人说话

本文件供调用方处理意图、来源和交付。独立作者主要读 [作者任务](author.md) 与相近语气样例，不用把这里的复核项目全部变成写作目标。

## 中文口语

个人账号默认在跟人说话。按这次场合保留反应、偏好、情绪和说话对象，不要求每条贡献一个方法或道理。清楚不等于背景齐全：独立帖须能单独读懂，回复可以借用原帖的主语和对象。读者需要倒回去猜意思时才补关系；正常的省略、停顿、感叹和重复可以保留。

材料可以完整，正文可以只取一处。一个事实或麻烦已经使读者理解作者为什么在意，不用再加“我会如何处理”。反过来，用户明确要讲方法或分析，就把理由说清。批量稿总是“复述材料—我的看法—给出办法”，应重新从原材料写，而不是只改句尾的语气词。

## 开头怎么说

有明确判断时尽早说，保留用户喜欢的 [A 组方向](voice-examples.md#用户偏好的观点帖写法)。这是开口偏好，不要求每帖先造一个主张。事实、发现、经历和问题也能直接开口。先说最想说的，再补读者确实需要的上下文；不要把资料收集顺序当成叙述顺序。

观点强度来自具体取舍。只把“方便、便宜、可靠都很好”讲得更肯定，不会变成有意思的观点。结尾可以补关键条件、后续动作或情绪，也可以没有结尾段。不强制总结、反转或提问，参照 [结尾的作用](voice-examples.md#结尾的作用--合成对照)。

## 回复是在接话

先看对方这条在分享、求助、庆祝还是争论。作者要收到原帖相关原文和重要的已见回复，不能只拿到一个主题摘要。回复连着原帖读：真正的问题有没有得到回答，异议是否针对对方实际说过的话，建议是不是他已经写过的？准备反驳某个词或一句话时，连同原帖前后已有的限定、例外和处理办法一起核对，别把作者已区分的情况合成一个靶子。

有具体反应就能接，不必另立一套办法。求助按需给方法；作品分享可以聊它本身，庆祝可以接住高兴。自动寻找机会仍需有对象明确的内容，不能批量刷“厉害”“我试试”。不把陌生人的分享自动改成对他的采访、考评或下一步安排。

引用面向自己的读者，补他们需要的背景；回复借原帖上下文；新帖独立成立。三者分别写，不把同一段短评到处粘贴。

## 内容从哪里来

用户给了观点、经历或问题就使用；没给也能从账号方向自主选题、提出判断。可以纯观点、反例、吐槽或假设，不需要先补一段亲身经历。事实材料支持相应事实，不决定全文结构；没有来源就不增加具体外部能力、数据、测试结果或“大家都”的断言。

开放选题按 [angles.md](angles.md) 比较不同主张，先选出值得说的内容，再参考语气样例写正文。“自然、通顺”和“有信息、有判断”分开检查：一条完全正确的常识，也可能没有自动推荐给读者的理由。观点在第一句只改变顺序，不会自动增加内容的分量。

明确的常青观点不要求借热点；用户指定新闻摘要、教程、庆祝或材料改写时，按那个目的写。很小的偏好也可以按要求表达，不把开放选题的筛选门槛变成拒绝用户明确任务的理由。

数字只取支撑核心意思的部分，保留样本、单位和比较对象。不同计数对象不能直接相减或接成同一个总体，关系未交代就分开说，或只用关系明确的那组事实。发现可来自观察材料，不要求亲测；分清文档支持的能力、推出来的用途和已验证的结果。转述事实材料时，不把别人的测试改成“我试了才发现”，也不凭空加“居然没人注意到”。

把技术能力讲成日常用途时，核对例子里的实际动作和结果：原有能力够不够，中间还需要什么？“支持导出”本身并不保证另一款软件能完整导入。影响这次用法的条件放回正文，或换一个能力确实支持的场景；不必讲实现细节，也不要把本来成立的发现全部改成免责声明。参照 [意思也要对上](voice-examples.md#意思也要对上--合成对照)。

资料包可以完整，正文只取这次要说的一点。数据型个人帖可以从最在意的结果开口，背景随后按需补。不要求说明它对行业、产品或读者有什么启示。选数字的方法见 [数字样例](voice-examples.md#从数字里挑出真正有用的结果)。

让相关读者愿意接话，可以来自他们经历过同样的问题，也可以来自他们不同意某个具体判断。需要主动邀请参与时，按 [participation.md](participation.md) 把要聊的对象和容易回答的那一点写清楚；问题本身也可以是有价值的内容。不是每帖都要提问，有用到值得保存的内容也成立。不许编“业内都这么想”来制造冲突，也不靠辱骂、骗互动或夸大承诺填补内容。

## 创作与事实任务

本账号允许创作性代写：日常小事、第一人称经历和人物对话可以编，正文可以直接说“我昨天……”，不必用“假如／想象一下”开场或加虚构声明。是否写故事取决于内容；不要为了利用这项授权，把每个观点改成亲历、把每条都写成段子。情节服务于想说的话，少塞无关细节，不在故事后补一段人生道理。

这项授权随本账号的普通创作调用沿用；其他账号按各自要求。用户指定真实、实测、仅按材料改写，或当前任务是在转述某份事实来源时，按事实写作，不借创作授权改动数据、归属和条件。真实产品能力、外部新闻、来源链接与执行结果仍须有相应依据。

把创作范围一起交给作者：哪些情节可编，哪些事实要保留。作者不能把已授权的第一人称故事一律改回假设场景。复核与历史记录中，创作情节不算真实用户经历、测试证据或实际工具操作；无需把内部分类塞进正文，也不把创作情节存成用户履历。

## Contrarian angles

敢讲有理由的不同意见：针对一个具体说法、惯常做法或真实讨论，指出反例、漏掉的条件或不同取舍。用户给了信念就保留它的力度；没有给时可以提出可辩护的判断，别编“我一直坚信”。

反共识要有实际对照。没有证据说明别人持相反观点，就直接说自己的主张。保留会改变意思的样本、条件和反例，不能把局部观察扩成普遍结论。如果正文已经把判断限定在某次测试或某个场景，不必再附“长期效果未知、其他情况未测”这类与当前主张无关的结尾；这些信息可留在复核中。若缺失条件会误导读者，仍须在正文说明。观点可以尖锐，事实不能跟着加码；“我认为所有人都已经……”仍是在断言外部事实。

争议只是可选切口。自动选题时，有用的回答也可能比反驳更适合。点赞、争吵或大号转发不能单独证明内容好或能涨粉。

## Attribution and added value

分清三件事：

- 核验：事实依据和 URL 留在正文外的复核信息。原创观点、用户提供的经历或授权创作可以没有公开来源，创作不充当核验依据。
- 署名：借用特定作者的成果、数字、引语、论点或演示，用自然的话说明是谁的。原生引用有时已经提供这一上下文。不要把借来的东西写成自己的发现。
- 给读者入口：默认不往评论正文塞研究链接。用户明确要分享资源，或查看特定原文就是这条帖的目的时，再放正文链接。署名不等于必须附一个 URL，链接也不能代替解释。

厂商展示、作者自述、自己的判断分清楚。保留影响含义的版本、条件、日期和限制；无关审计信息留在复核中。视频没看过就不写“视频展示了”；设想的失败不写成已知产品缺陷。转述要简洁，保留许可要求，不做整篇翻译或逐句换皮。

## 独立成稿

支持且允许子代理时，把唯一一次写作委派用于第一稿（`fork_context: false`）。研究调用方不先写正文，给作者以下材料即可，不必造新 JSON：

- 用户这次的要求、账号语气、输出形式和创作授权；**明确标出用户指定的立场**，没有就写未指定。
- 用来写的事实、具体事件、原帖相关原文与已见回复。写明哪些是来源作者的说法、设想或尚未核实；不用把研究过程和全部材料搬来。
- 与交流场合相近的少量语气样例，保留它们的原帖背景。样例只教表达，不能借走经历、事实、身份、关系和口癖。

上游 Agent 自拟的 `angle`、标题、道理、提纲、待保留的“核心意思”，不放进必须保留项。需要供作者了解时标为可舍弃建议。用户自己的观点、指定的内容价值和事实条件不能以“换个自然说法”为由丢掉。开放选题的作者应自行判断最值得说的东西，不能把一条没有具体意思的赞同作为成品。

把 [author.md](author.md) 路径与材料一起交付，说明当前 Agent 就是独立作者，不再委派。作者只需这份简短任务、按交流场合选择的样例和 Humanizer 的相关条目；不必读调用方的选题、验收与调度规程。附上本次允许使用的工具、输出方式和事实／创作边界，不联网补事、不操作账号。调用方负责格式包装、来源记录和最终长度检查。

明确要求改现有文案时，可以交用户提供或已认可的原稿及修改要求；这是编辑任务，不必推翻原意另写。不要把这一例外用于保护 Agent 刚生成但用户未认可的稿子。无可用子代理时，当前 Agent 使用同一份材料和任务独立成稿，不伪称干净上下文。

## 成稿复核

调用方只修实际存在的问题，不能把“更完整”当成二次改写的理由：

- **话在对谁说？** 回复连着原帖读，独立帖单独读。含义应顺着能懂；人物称呼、动作关系和词语搭配也要自然，不能只因猜得出意思就通过。只指出实际含糊或生硬的地方，不逐句补主语，也不把正常技术词和比喻一律换掉。
- **这句话为什么要说？** 一个有对象的反应、反例、发现、问题或判断都算；“说得对，所以大家应该……”这类换哪个帖子都能用的尾巴没有增加交流。用户指定的庆祝、教程和小意见按要求完成。
- **有没有把材料写歪？** 核对来源归属、数字对象、必要条件、创作范围。主张的办法应能处理所说的麻烦，推出来的用途不能多承诺一个没有支持的能力。
- **说顺了，还是只把段子排整齐了？** 看是否为了讲一个普通观点，额外搭了活动设定、规则和压轴包袱。设想和笑话本身不是问题；笑点若靠偷换前面的概念才成立，不能因为句子好懂就放过。先核对具体意思，不用“程序员有共鸣”替代检查。
- **是否仍有自己的意思？** 强观点别被改成愿望或索取更多细节；问题别被自己答完。本文没必要解释的推理可以留给交流，不要求每条都有起承转合。

Humanizer 用于找具体毛病，不是身份检测器。它的“信息”也包括情绪、关系和对话动作；不要为了每句新增事实而给一句自然接话添解释。语气词、感叹、正常重复、对比或短句都不能单独判为错误。自然的原句不必换成更正式、正确或漂亮的表达。长度、图片和事实检查各自报告，不当作自然度证明。

修改事实错误或读不懂的地方后重验最终文字；不把结果交给一串评委连续修稿。维护测试保留第一份完整交付，包括失败稿。外部测试反馈只能用于下一次 Skill 修订和新的独立试跑，不能喂回原作者。用户明确否定的稿子不会因模型给高分而变成成功样例。
